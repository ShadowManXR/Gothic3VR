# 0.22.23 — scene refresh and zone preloading diagnostics

Scope follows the user's request to focus on the large100–230ms native scene hitches. Bow and projectile logic, including their existing timing, remain byte-identical to0.22.22. This release adds measurements, not a proven fix or FPS gain.

The0.22.22 capture showed gameplay native-eye stalls231.4ms(left),166.2ms(right),114.0ms(left),102.6ms(right). Most of each interval was inside RenderSystemAdmin::Render but outside the four original draw APIs and outside the measured frustum Extract/Execute work. That does not isolate pure CPU work or prove a resource-streaming root cause.

Add four hash/export/RVA/prefix-verified native hooks: FrustumDatabase::RefreshFrustumData, PVSPrefetcher3::Process, PVSPrefetcher3::Execute, and PVSPrefetcher3::WaitForEmptyThreadQueue. These split the previously unmeasured parent into scene-data reset, zone-prefetch processing/execution, and its public queue-drain operation. Every wrapper calls the original exactly once; Process preserves its native boolean result. Work on other threads/outside the original application-thread eye scope continues without collecting timings. No resource job is skipped, reordered, canceled, forced synchronous or moved to another thread. Unknown/mismatched entry points skip only that profiler. The startup mask now has9bits(update,extract,extract_oc,execute,render,refresh,pvs_process,pvs_execute,pvs_wait);511means all9installed, not that every export is called by this engine path.

Native phase reports add frustum_refresh_inclusive, pvs_prefetch_process_inclusive, pvs_prefetch_execute_inclusive and pvs_prefetch_wait_inclusive. The existing native analyzer handles them without changes, including mixed/missing older phase names. Inclusive nested values overlap; a200ms wait inside a230ms Process must not be reported as430ms. The existing per-eye/frame/QPC spike records allow correlation. Logging remains deferred until after the measured eye's CPU scope and GPU end timestamp close. A zero call count means no observed call through that export in this scope; it is not proof of no loading or waiting elsewhere.

The existing same-frame transfer fences, both-eye frusta, native culling/scene lists, resolution, settings, tracking, audio, weapons and skill progression are unchanged. Native resource/thread scheduling is unchanged pending evidence about where the large parent stalls occur.

DXVK compatibility is researched separately in DXVK-SCENE-NOTES.md. The current D3D9Ex→native D3D11 shared-resource bridge fails with the tested DXVK path on Windows (recorded0x80070057). DXVK's Vulkan interop interfaces and VDXR's Vulkan backend offer a possible future integration route, but that requires a graphics-backend implementation and a separate proof; it is not enabled in0.22.23. DXVK's benefit for the actual observed large native stalls is unproven. No DLL is dropped into the game and no runtime/layer registration is changed.
