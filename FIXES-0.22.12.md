# Gothic3VR0.22.12 — remove per-scene particle query overhead

0.22.11 introduced a serious performance regression. Its global particle callbacks did live SDK/player/weapon/ancestry checks, including VirtualQuery once per name byte, on eligible emitters across the whole scene even without a held Flame Sword. The user reported severe stutter. Saved sessions show median first-person stereo submission rates62.7/s in the earlier0.22.10 session and21.9/s/24.8/s in the two0.22.11 sessions, without any Flame Sword suppression log entries. These are different live sessions, not a controlled benchmark or a headset frame-time measurement. The exact known-good0.22.10 DLL was immediately restored while preparing this fix, without closing the unchanged launcher or altering settings.

The particle callback now checks application-thread identity and a fixed list of at most8 exact particle addresses. It does not call the SDK, query memory, read any particle/name/owner object, allocate or traverse the world. The empty list is a fast no-match. A cold pass builds that list once per tracked frame from only the current player's tracked held1H Flame Sword/Magic Flame Sword descendants. Other weapons return before any child traversal. Collection is bounded to64 nodes per root, validates child-parent ownership, and refuses invalid/cyclic/overflowing trees. Names use one bounded bulk memory check, rather than per-byte VirtualQuery. The accepted exact01/04 independent/non-instanced layers are selected; local02/03 flame/glow still stay native. Collection failures preserve all native effects.

The address list clears at every outer camera render before readiness checks, at BeginTrackedArms, on VR stop and before native world teardown. This includes failed stereo preparation, menus, tracking loss, activities, native rendering, save transitions and shutdown. Worker callbacks do not read application-thread cache state. No entity/property pointer is dereferenced by the hot filter. Existing particle hook prologues and x86 callback ABI are unchanged. Menu staff hiding remains and all hand/palm/2H/handling/ranged/skill/input/camera mechanics are byte-identical to the accepted versions.

78/78 tests pass. New regression covers cache lifecycle, corrupt/foreign/cyclic trees, bounded capacity, dual wield, no traversal for normal weapons and two million unrelated emitter address lookups with ZERO object/name/property/owner/memory queries. The synthetic lookup took4.553ms in this build; this is not an in-game FPS measurement. Existing real x86 callback tests now execute the actual address-cache forward/skip branch over10000 cycles. All77 previous tests, including real native hook bytes and accepted hands, pass. A source check also rejects SDK/memory calls in the actual SkipOwnedFlameTail body.

Launcher and resolution patch remain byte-identical; existing15-page UI evidence is retained with provenance. User INI is preserved byte-for-byte. The installer allows the unchanged launcher to remain open and guards that the game is closed. No game/headset probe is launched automatically. Runtime logs identify bounded_target_cache. Gameplay fluidity and the retained Flame Sword/menu-staff changes still need a live headset check; no recovered FPS is claimed yet. See flame-performance-evidence-0.22.12.json for evidence and limits.
