# 0.22.25 — Restore native camera threading for PUP in stereo

The0.22.24 live capture activated the PUP hook, but every one of53856 eye-scope work calls bypassed the budget. Gameplay PUP work peaked at28.57ms while an enclosing PVS call reached277.45ms inside a282.22ms eye. The previous policy did not address that remaining large synchronous work. No controlled improvement is inferred from different session maxima.

The native eCCameraBase::Render FIRST bool is a threading allowance, not a freeze flag. Our stereo renderer passed false for both eyes, disabling the engine thread pool and making PVS dispatch synchronous. PUP then intentionally sets its force flag and drains maintenance without a time slice. Engine.dll disassembly proves the first-argument load atRVA5ef05, global pool write at5ef1c, distance-based false fallback at5ef01 and PVS synchronous dispatch at1a6cae. PUP's IsThreadingEnabled inversion is at116b9–116c1. This is an integration bug, not evidence that PUP's own scheduling is broken.

With the exact supported PUP profile active, eye rendering now forwards the caller's original threading allowance instead of forcing false. The second argument stays true for each eye's rebuilt frustum. The engine still controls its camera-distance fallback and all forced/loading calls keep their native arguments. The pre-stereo pool state is restored in the outer __finally, including partial-frame failures. There is no unconditional thread enable, manual worker creation, native job replacement, queue drop, shared-eye render list or removal of synchronization. Unknown PUP profiles and G3VR_PUP_COMPAT=0 keep the prior synchronous stereo path.

The0.22.24 nonblocking optional queue admission and soft2ms allowance remain shared across both eyes. Complete items can still overrun, and native mandatory work/waits may still stall. The correction enables the native asynchronous path where the caller permits it; it is not a guarantee of hitch elimination. A new vr_pup_threading line reports cumulative world-eye requests and forced/optional work counts in context1. Startup also reports native_camera_threading=1. The existing vr_pup_prefetch and native phase timings remain available.

Validation:95/95 tests passed (final run7.79seconds), analyzer fixtures passed and the compiled DLL passed the native FMOD audit; unsupported getPan is absent. Exact Engine-file validation now checks the real camera threading argument, native distance fallback, thread-pool getter/setter and PVS dispatch flag. The camera trampoline test now uses actual ECX/self plus two stack booleans and all four argument combinations. No engine DLL is executed by those file tests. Existing gameplay, audio, bow, arm calibration, stereo frusta and graphics fences stay unchanged. User settings, PUP DLLs/configuration and the accepted launcher are preserved.

Live verification: traverse the same route for3–4minutes and check that terrain, objects, NPCs and textures keep loading normally. Inspect eyes_allow/eyes_sync and forced/optional counters, admitted/deferred work and same-eye/frame PVS spikes. Offline tests cannot prove live asynchronous execution or FPS improvement.
